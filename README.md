# 视觉小说生成管线 · 开发路线图

状态：初稿，供后续设计和开发使用。

这是一条半自动制作视觉小说的管线。从原始文本出发，先产出可以逐幕审阅的剧本，再生成、筛选并挂载资产，最后编译为实际游戏引擎可以运行的工程。长期目标是让作者能在同一个项目里反复修剧本、补资产、换模型和换引擎，并能看清每次修改影响了什么。

## 1. 已定下的架构

| 层或产物 | 职责 |
| --- | --- |
| Raw text | 改编输入。这里可以是小说式叙述，或还没有拆幕的草稿。 |
| Scenario | 人可读、可编辑的文学剧本。写清楚每幕的上下文、读者看到的文本、人物台词，以及会影响后续制作的舞台意图和剧情流程。 |
| 结构化 Scenario | 从 Scenario 确定性解析出的引擎无关表示。保留剧情、展示和控制流的含义，尚未绑定具体资产。台词停顿、富文本等增强可以由 LLM 辅助，按预算启用。 |
| Script | 在引擎无关表示上绑定已批准资产后的脚本。未绑定的资产直接省略绑定，部分挂载的脚本也应可编译和运行。 |
| 引擎工程 | 由编译插件把 Script 转为实际目标引擎的工程。预览走真实引擎，由人手动触发。 |

同一套后端管理管线状态、闸门、项目资源和绑定。统一 UI 负责编辑、审阅、筛选、管理资源和组装。VS Code 与 Agent/Skill 可以通过同样的操作契约接入。生成模型可以按资产分支替换。编译和预览各自保留插件边界。

## 2. 先把 Raw text → Scenario 做扎实

这一步决定后面有什么可以解析、生成和挂载。模型在这里承担改编工作。它要把原文转成玩家能按顺序读到的内容，并把会影响演出的信息显式写出来。之后的解析只按剧本文本读出已经写明的含义。

| 原文里的信息 | 改编时怎么处理 |
| --- | --- |
| 角色说的话 | 写为 `说话人（动作）：内容`。说话人用于识别角色台词，动作保留可供演出判断的信息。 |
| 环境描写、第一人称叙述、内心独白 | 需要让玩家读到的部分可以作为无说话人的文本展示。旁白不配音。只有在会改变背景、立绘、声音等演出时，才另外写明舞台意图。 |
| 叙述者是谁 | 可用人物列表里的 `*` 等编辑标记帮助作者理解。这个标记本身没有脚本行为。 |
| 场景切换、人物出入场、背景或音乐变化 | 把可读的场景上下文和实际需要执行的舞台变化写清楚。场景元信息是否自动触发舞台动作，留待语义验证。 |
| 剧情选项和跳转 | 原文或作者已经明确的控制流应显式保留。遇到原文没交代的去向，交给作者在 Scenario 审阅时决定。 |

目前的写法用 `<>` 分段，`[]` 写舞台控制，`{}` 写脚本控制，普通文本与台词穿插。这是语法样稿，具体指令、标点兼容规则和 IR 字段都留待验证。

```text
<1:2
时间 : 深夜
地点 : 车站候车室
人物 : 林岚*、周明（羽绒服）
>

雨敲着玻璃。

我抬眼，看见周明站在门边，手里捏着一张车票。

我（压着火）：你还知道回来。

[周明上场]
周明（把车票翻了个面）：末班车还没走。

他还是没回答我的问题。
[音乐]
</1:2>
```

改编验收时，把原文与 Scenario 并排检查。先确认剧情事实、台词归属和叙述顺序，再检查哪些环境细节留在文本里，哪些应该变成舞台指令。样稿里的 `我` 若需要按角色配音，应能在作者审阅时明确它对应哪个角色。星号只帮助读者辨认视角。如何表示说话人别名，以及 `[音乐]` 何时需要补充意图，都应拿样例讨论后再定。

## 3. 把资产需求和人工决策接到剧本上

1. **从剧本提取制作需求。** 人读的摘要按全文、章节、场景组织。供生成使用的摘要按分支挑出所需背景，例如人物外观与性格、场景环境、作品的音乐基调。两种摘要各自服务于不同读者。
2. **先定 Tag，再生成候选。** Tag 描述剧本需要的资产，在构造 Prompt 时确定。表情和音乐分别使用受控词表。角色有基础表情，也可以根据人物摘要扩展自己的表情枚举。Script 使用词表允许的值。
3. **按媒介组织生成输入。** Prompt 由相关文本摘要、同媒介参考和人工补充提示词组成。软件级画风参考可以供项目复用。项目内从角色设计到基准立绘，再到差分和 CG，沿用上游确定的外观。TTS 以角色为单位复用音色母本。参考音乐可先提炼为生成提示。
4. **在创作性环节设闸门。** Scenario、资产 Prompt、候选和挂载结果都要有审阅机会。默认等待人工决定，可显式放行。打回退到当前闸门的直接上游。候选未获批准时留在候选池，批准后才能作为该需求的可用资产。
5. **允许部分挂载和增量更新。** 背景通过就能先挂背景，角色语音可以晚些通过，也可以省略。后续补配音时应保留已通过的背景。若已挂载资产被打回，原型要能验证对应绑定的撤回。上游修改波及哪些批准记录，需用实际编辑样例明确。

## 4. 按可验收的阶段推进

以下顺序是开发建议。每阶段保留一份输入样例、预期输出和未定规则，供以后复跑。

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| 0 · 剧本样例 | 先做小批原文与人工改编的 Scenario 对照。覆盖同场多轮台词、无角色文本、人物出入场、场景切换和选择跳转。 | 作者可以逐幕校对。样例标出文本、舞台指令与脚本控制的边界，并列出暂时需要人工决定的地方。 |
| 1 · 语法和 IR | 用真实 Galgame 场景和目标引擎的脚本样例验证语义。先确定最小共同表示，再写解析与校验。 | 同一 Scenario 得到同一结构。错误能定位回原文行，场景、台词、舞台控制和跳转可逐项核对。词法和结构的暂定部分有明确标记。 |
| 2 · 单场景原型 | 选一个实际引擎验证编译与手动预览。用准备好的候选资产跑背景和角色语音两条分支。 | 一条背景候选被打回后可以重新提交。批准背景、语音待审时，工程仍能运行。随后批准语音并重新编译，原背景绑定保留。 |
| 3 · 多场景编辑与资源管理 | 扩到多幕和多角色。统一 UI 支持审剧本、看候选、校对挂载、管理资源与预算。处理局部剧本修改和已批准资产的撤回。 | 只改一幕或打回一项时，能看出受影响的需求及绑定。未受影响的内容保留，修改后的项目可再次编译和预览。 |
| 4 · 接入真实模型 | 逐条把候选生成替换成实际模型调用。先挑一条分支验证 Prompt、参考和筛选，再扩展到其他媒介。 | 实际生成结果能进入同一套审阅和挂载流程。单条分支生成失败后可重新执行，其他已批准分支可以继续。 |
| 5 · 增加引擎与入口 | 从一个能跑的工程扩到第二个引擎，再按需要接 VS Code 与 Agent/Skill。 | 同一 Scenario 和 Script 可按两个引擎各自支持的范围编译，差异可解释。不同入口看到一致的项目状态和闸门结果。 |

阶段 2 是第一个可演示的完整成果。可以先用确定的候选资产检验审批和部分挂载，再拿真实生成结果衡量改编、提示词和筛选的质量。两类验收分开记录。

## 5. 用样例推动待定问题

| 待定问题 | 先用什么判断 |
| --- | --- |
| 场景头的时间、地点、人物是否具有演出语义 | 写两幕发生在同一地点但舞台表现不同的戏，区分作为上下文的信息和真正需要执行的动作。 |
| 人物身份、说话人别名、立绘和 TTS 如何对应 | 用第一人称主角、同一角色的两个称呼，以及只有台词没有立绘的角色做对照。 |
| `[]` 的最小指令集和 `{}` 的控制流边界 | 用出入场、表情切换、音乐变化、分支后汇合的真实脚本样例，确认哪些需要共同语义。 |
| 剧本修改后，哪些需求和绑定可以沿用 | 分别试改台词、移动一幕、更换角色衣着、撤回一条配音，比较每次应重新审阅的范围。 |
| 跨引擎如何处理缺失资产与能力差异 | 分别去掉配音、背景和立绘，在候选引擎里实际编译和预览，记录每种缺省情况下可接受的表现。 |
| 生成预算、插件和多入口写入的细则 | 在单场景跑通后，结合真实模型成本、第二个引擎差异，以及两个入口同时操作同一项审批的例子再定。 |

## 6. 后续开发如何使用这份路线图

下一次从阶段 0 开始。以车站场景为第一条样例，补一条跨场景跳转或选项，再补一条同角色跨幕复用立绘与音色的样例。每条样例都保留原文、审定后的 Scenario、预期展示顺序，以及预期产生的资产需求。先解决导致不同理解的语义，再让解析器或下游模型依赖它。

交给开发 Agent 时，一次指定一个阶段或一条可验收的流程。完成后在本文记录实际跑过的样例、确定的新规则、仍未解决的问题，以及下一步可以复用的产物。具体技术选型随验证结果记录。阶段完成以验收结果为准。
